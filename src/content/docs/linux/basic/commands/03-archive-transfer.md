"把日志目录打包传到另一台机器"是运维的日常，也是面试里 Linux 实操环节
的常客。本篇覆盖两件事：**打包压缩**（tar 家族）与**远程传输**（scp/rsync）。

## tar：一堆文件变成一个文件

tar 本身只负责"打包"（多个文件合成一个归档），压缩靠搭配 gzip/zstd。
参数记忆法：**c 创建、x 解开、t 查看清单，v 显示过程，f 后跟文件名——
f 必须紧跟文件名**。

```bash
tar -czvf logs.tar.gz logs/        # 打包并 gzip 压缩（c-z-v-f 口诀）
tar -tzf logs.tar.gz               # 先看清单（不解开，防覆盖）
tar -xzvf logs.tar.gz -C /target/  # 解压到指定目录（-C 大写）
```

- **解压前先 `-t` 看清单**：归档里若带绝对路径或 `..`，直接解可能覆盖
  系统文件——这是老牌安全坑。
- 常见后缀对照：`.tar.gz`（= `.tgz`，gzip）、`.tar.bz2`（-j，更慢更小）、
  `.tar.zst`（-zstd，现代平衡）。

## 压缩率与速度的权衡

| 算法 | 速度 | 压缩率 | 场景 |
| --- | --- | --- | --- |
| gzip | 快 | 中 | 通用默认 |
| bzip2 | 慢 | 较高 | 归档不常用 |
| zstd | 极快 | 高 | 现代首选（见 Kafka 压缩篇同一权衡） |
| xz | 很慢 | 最高 | 极限省空间 |

压缩是 CPU 换带宽/磁盘的权衡——**热数据用快的，冷归档用狠的**，
和消息队列选压缩算法是同一套思维。

## scp：简单直达，rsync：增量同步

```bash
scp app.log user@host:/tmp/                  # 简单复制（全量）
rsync -avz logs/ user@host:/backup/logs/     # 增量同步（推荐）
rsync -avz --delete src/ dst/                # 目标随源删（危险，先 -n 预演）
```

- **rsync 为什么快**：先比对两端文件的大小/修改时间（可加校验和），**只传
  差异部分**，甚至文件内部只传变化块——scp 每次全量复制，rsync 第二次起
  几乎只传增量。
- 生产纪律：`--delete` 会把目标端多余文件删掉，**永远先 `-n`（dry-run）
  看会删什么**——和 sed -i 先备份是同一条命。
- 常用组合：`-a` 归档模式（递归+保留权限/时间戳/软链），`-z` 传输压缩，
  `-P` 显示进度+支持断点续传。

## 高频追问速答

- **tar 的 -f 为什么必须在最后？** -f 的参数是文件名，紧跟其后；写成
  `-fc x.tar` 也行但 `-fx` 会把 x 当文件名——顺序错是 tar 报错的头号原因。
- **rsync 和 scp 怎么选？** 一次性小文件 scp 省事；目录同步、大文件断点、
  定期备份一律 rsync——增量特性在第二次以后收益巨大。
- **打包要排除某些文件？** `tar --exclude='*.log' -czvf ...`——排除模式
  放在源路径之前。

## 小结

- tar 口诀 c/x/t + v + f；解压前先 -t 查清单防覆盖。
- 压缩算法是速度与压缩率的权衡：默认 gzip，现代选 zstd。
- scp 全量、rsync 增量；--delete 必须先 -n 预演，-a -z -P 是生产三件套。
