## 集群：broker 间怎么协作

RabbitMQ 集群**只同步元数据（交换机/队列/绑定），默认不同步消息内容**。
节点间在 25672 端口通信，任意节点可被客户端连接：

```mermaid
flowchart LR
    N1["节点1"] ---- N2["节点2"] ---- N3["节点3"] ---- N1
    C["客户端"] -->|"随机/负载连任一节点"| N1
```

- **普通队列**：消息只落在声明它的节点，其他节点只存引用 → 该节点挂了，
  此队列消息不可达。集群只能算"能连"，不算"高可用"。
- **镜像/仲裁队列**：消息在**多个副本**节点冗余 → 才能扛单点故障。

## 镜像队列 vs 仲裁队列

| 特性 | 镜像队列（经典） | 仲裁队列（Quorum，3.8+ 推荐） |
|---|---|---|
| 一致性 | **异步镜像**，可能落后 | **Raft**，强一致多数派 |
| 故障 | 主节点挂了可能丢"镜像未同步"的数据 | 多数派存活即可继续 |
| 适用 | 低延迟大吞吐 | 可靠性优先 |

新项目直接用 **仲裁队列**（`x-queue-type=quorum`），它用 Raft 在多个副本间
保持一致，避免经典镜像的"半同步"丢数据问题。

## 脑裂 / 分区感知

网络分区（节点互相看不到）时，RabbitMQ 默认会**暂停/分区**以避免数据撕裂。
可配置分区策略；生产实践上：

- 节点奇数个，配合 **多数派仲裁**，分区后一侧继续、另一侧暂停。
- 用 `rabbitmqctl` 观察分区健康，避免盲目扩容引入更乱的脑裂。

## 消费端常见问题

- **单一昂贵的消费者**重活累活全卡它 → 用 `prefetch` 限制 unacked 数量，
  配合多消费者**并行负载分担**（单队列多条消费者默认轮询分发）。
- **连接/Channel 泄漏**：用完不关 Channel，连接数打满。用连接池复用。
- **自动恢复（topology recovery）**：broker 故障后连接恢复时自动重建
  交换机/队列/绑定，别自己写一堆恢复代码。

## 吞吐到底由谁决定：prefetch 与消费者的建模（深入）

很多人把"加大群消费者数"当唯一的吞吐杠杆，其实瓶颈往往在 **prefetch
（未确认消息上限）**。先理解一个队列的场景规律：

> **同一时刻，一个队列最多能"在途"的消息 ≈ 消费者数 × 每个消费者 prefetch**。
> 小于这个，消费者就有空等；大于这个，消息才在队列里排。

```java
channel.basicQos(20);   // 每个消费者最多同时 hold 20 条未确认
```

**逐个调参看效果：**

| 调整 | 效果 | 隐患 |
|---|---|---|
| 增大 prefetch | 消费者一次多取、少往返 | 内存占用↑，单条慢会压一堆 |
| 增加消费者数 | 总在途↑，分担负载 | 需要队列有足够并发语义 |
| prefetch 太小（如 1） | 每条都等 ACK，吞吐被 RTT 卡死 | 典型的"慢"帮凶 |

**建模口诀：`目标吞吐 = 消费者数 × prefetch / 单条处理耗时`。** 例如要
`500 msg/s`、单条要 20ms（即 50 msg/s·消费者）→ 需要约 10 个消费者；
若每个 prefetch=5，则每消费者 250 msg/s，5 个消费者就够。先算再调，比堆
盲目加消费者高效得多。

### 慢消费者才是雪崩之源

一个 prefetch 很大的慢消费者，会**占住队列里的在途额度**，把其他消费者
"饿死"。排障顺序：

1. 看 `channels`/监控里每个消费者的 **prefetch 与 unacked**。
2. 某个 unacked 长期顶格 → 它处理太慢，而不是队列吞吐不够。
3. 对应调小它的 prefetch，或拆分消息粒度，而不是加机器。

## 小结

- 集群默认只同步元数据；要扛单点必须用镜像/仲裁队列。
- 仲裁队列基于 Raft 强一致，是新项目首选。
- 消费端靠 prefetch + 多消费者并行 + 连接池 + 自动恢复来扛住吞吐与故障。
