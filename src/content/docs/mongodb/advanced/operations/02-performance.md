## 索引优化与 explain

没有索引的查询就是 COLLSCAN（全集合扫描），数据量一大就是灾难。
**优化前先让证据说话**：

```js
db.orders.find({ userId: "u42" }).sort({ createdAt: -1 }).explain("executionStats")
```

看三个数的比例：`totalKeysExamined : totalDocsExamined : nReturned`，
理想是 **1:1:1**；出现 `COLLSCAN`、或 examined 是 returned 的成百上千倍，
就是索引没建对或没走到。

建索引的三条纪律（来源 5 的原则 + 现代实践）：

1. **越少越好**：每个索引都要在写入时维护排序，索引多了写放大明显——
   每个索引都必须被至少一类查询用上，否则删掉；
2. **复合索引前缀复用**：`{a:1, b:1, c:1}` 同时服务 a、(a,b)、(a,b,c)
   的查询与排序，不必重复单建；排序方向可整体翻转（`{a:1}` 也能服务
   a 降序），不必为方向重复建；
3. **高选择性字段靠前**（ESR 原则：等值 → 排序 → 范围）：低基数字段
   （一半文档都是同一个值的字段）放最前，索引几乎过滤不掉数据。

进阶：查询与投影字段全部落在索引内 → **覆盖查询（Covered Query）**，
免回表，`totalDocsExamined` 直接归零。

## 文档模型：设计期就决定了性能上限

MongoDB 没有 join，靠文档内嵌与拆分的取舍（来源 5 的三档）：

| 方案 | 结构 | 查 | 改 |
|---|---|---|---|
| 完全分离（范式化） | 图书只存作者 id，两个集合 | 两次查询拼装 | 作者信息只改一处 |
| 完全内嵌（反范式化） | 作者整体嵌入图书 | 一次查询拿全 | 作者改名要遍历改所有图书 |
| 部分内嵌（折中） | 只嵌入常用的姓名等字段 | 常用信息一次查到 | 冷字段去作者集合改 |

选择依据是**该集合的读写比**：日志类（写多读少）偏分离；商品展示
（读多改少）偏内嵌；多数业务用折中——把"几乎不改的常用字段"嵌进来，
把"频繁改的字段"留在独立集合。

三条硬边界：

- **文档上限 16MB**，但实际经验控制在几十 KB 级——大文档的搬运、网络
  传输与更新重写都按整文档计价；
- **无界数组是大忌**：评论无限 push 进文章 → 文档膨胀、多键索引随之
  线性膨胀。拆出子集合，或只嵌"最近 N 条"、明细另存（subset 模式）；
- **深嵌套**：层级超过 3 层后，$ 定位符、索引与更新语句都难写难优化，
  嵌套控制在 2~3 层。

> 旧文常提 MMAPv1 的填充因子（padding factor）/ usePowerOf2Sizes——
> 那是文档顺序存储、一改就整体搬移时代的问题；WiredTiger 下文档移动
> 已大幅弱化，无需手工预留空间，但"控制文档与数组规模"的结论依旧成立。

## 慢查询定位：profiler

```js
db.setProfilingLevel(1, { slowms: 100 })   // 只记录 >100ms 的操作
db.setProfilingLevel(2)                    // 全量记录（有开销，短时诊断用）
db.system.profile.find().sort({ ts: -1 }).limit(5)
```

慢日志字段直接给出药方：`planSummary: COLLSCAN` → 建索引；
`keysExamined` 巨大 → 索引选择性差；锁等待高 → 并发冲突；`numYield`
异常 → 工作集在挤内存。配合 mongod 日志里的慢操作行（含时长与扫描量）
即可覆盖大多数定位场景。

## 大量集合启动加载慢：原理与规避（来源 6）

**现象**：集合数很大（如 10 万）时，4.2.0 及之前版本启动加载要 10 分钟
以上，初始常驻内存近 5GB；虚机/容器（cgroup 限额）场景甚至加载不完
直接 OOM——启动慢直接拉长故障恢复的 RTO。

**元数据加载链**：MongoDB 层把所有集合的 catalog 存在一张 `_mdb_catalog`
表里；它在 WiredTiger 眼里只是普通数据表——WT 自己的元数据表是
`WiredTiger.wt`，后者又依赖文本文件 `WiredTiger.turtle`。启动顺序：
turtle → WiredTiger.wt → _mdb_catalog → 逐个初始化集合。

**为什么慢**：旧版本初始化每个集合时用 `metadata:create` cursor 读
元数据——一次查找要对 WiredTiger.wt 的 btree 做 **3 次**从 root 起的
search；集合数 × 每集合多处调用，开销被数量级放大。

**官方优化**（已 backport 到 4.0/4.2）：

1. 两处改用 `metadata:` cursor——只需 1 次 btree search；
2. **延迟打开 cursor**——NextRecordId（下次插入分配记录 id 的依据）
   不再启动时逐集合反向遍历获取，推迟到该集合**首次插入**时再算。

效果：10 万集合加载 10 分钟 → 2 分钟（约 1/5），初始常驻内存
4.8GB → 1.2GB（约 1/4）。

**规避与启示**：

- 大量集合场景升级到含优化的版本；容器内存限额要按**启动峰值**（而非
  稳态）留；
- 海量小集合本身值得反思：多租户"一租户一堆集合"的模式在集合数上万后，
  元数据与维护成本远超收益——考虑按租户字段分桶进大集合。

## WiredTiger 调参要点

| 参数 | 默认 | 建议 |
|---|---|---|
| `cacheSizeGB` | 约 (RAM−1GB)×50% | 容器/cgroup 场景**显式设置**（旧版本按宿主机内存算会误判） |
| `blockCompressor` | snappy | 磁盘紧张换 zstd（压缩比更高，CPU 略涨） |
| 索引前缀压缩 | 开 | 保持默认，索引省一半是常态 |
| journal | 开 | 保持开启，`j:true` 写关注依赖它 |

调参顺序永远是：**先修索引与模型（收益最大），再对齐工作集与内存，
最后才是参数微调**——eviction 等内部参数的默认值通常已近最优，乱调
反而引入不可解释的行为。

## 小结

- 优化从 explain 的三个数开始：1:1:1 是目标，COLLSCAN 是事故。
- 索引越少越好，复合索引靠前缀复用；按 ESR 顺序建复合索引。
- 文档模型按读写比选三档内嵌策略；无界数组与深嵌套是两大反模式。
- 大量集合启动慢 = metadata cursor 开销 × 集合数；升级版本 + 控制
  集合规模。
- WT 调参先管 cacheSizeGB 与压缩，别碰 eviction 细节。
