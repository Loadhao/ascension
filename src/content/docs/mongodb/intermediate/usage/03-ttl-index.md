会话记录、临时令牌、操作日志——**"自动过期"是这类数据的共同需求**。
MongoDB 的 TTL 索引提供声明式过期（建索引即自动删），但三个坑要知道：
**删除不是即时的**、字段必须是日期、大批量过期有性能影响。

## TTL 索引：声明式数据过期

```javascript
// 建索引时声明：createdAt 超过 3600 秒的文档自动删除
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 })
```

- 原理：**后台线程每 60 秒扫描一次** TTL 索引，删除过期文档——
  所以过期是"分钟级"而非"秒级"（对照 Redis 的惰性+定期删除，
  缓存篇）；
- **字段必须是 BSON 日期类型**——存成字符串/时间戳数字，TTL 不生效
  （不报错，静默失效——最大的坑）；
- 场景：会话记录、验证码、临时令牌、事件日志按保留期滚动。

## 大批量过期的性能影响

同一时间到期的文档几十万条时，TTL 删除线程集中删除——**删除也是写**：

- 每个删除走 WiredTiger 写路径 + 索引维护——大批量过期会造成 IO 尖峰、
  影响正常读写；
- 缓解：**错开过期时间**（写入时给 expireAfterSeconds 加随机抖动，
  避免同时到期）；预留删除窗口的 IO 余量；
- 对比 logrotate 篇：日志滚动也在"删除旧文件"——**所有"自动清理"
  都要考虑清理本身的成本**。

## 三层过期治理对照

| 层 | 机制 | 典型场景 |
| --- | --- | --- |
| Redis | EXPIRE（惰性+定期删除） | 缓存、验证码（缓存篇） |
| MongoDB | TTL 索引（后台 60s 扫描） | 业务文档的保留期（会话/事件） |
| 文件系统 | logrotate / 生命周期规则 | 日志文件、导出文件（Excel/大文件篇） |

同一需求（"数据自动消失"）在每一层都有对应机制——**选层取决于数据
在哪一层**，跨层迁移时过期语义要重新设计（不能指望 Redis 过期了
Mongo 也过期）。

## 高频追问速答

- **TTL 能"到期立即删"吗？** 不能——60 秒扫描周期是设计使然；要求
  即时的过期语义（如验证码 5 分钟失效）应该用 Redis EXPIRE，MongoDB
  只做归档式清理。
- **过期但未删除的数据能查到吗？** 能——TTL 删除前数据还在，业务
  逻辑不能依赖"TTL 到了就查不到"（Redis 过期同理）。
- **改 expireAfterSeconds 要重建索引吗？** collMod 命令可在线修改
  （不用重建）——但只对新写入/未过期的生效语义要测试确认。

## 小结

- TTL 索引 = 声明式数据过期：**日期类型 + expireAfterSeconds**，
  后台 60 秒周期删除（分钟级非即时）。
- 大批量过期 = 删除风暴（IO 尖峰）——写入时加随机抖动错峰。
- 三层过期对照（Redis/文档/文件）："自动消失"在每层都有机制，
  按数据所在层选。
