基础索引进阶篇（MySQL 对照）之外，MongoDB 有几个**特色索引类型**：
部分索引（只索引部分文档）、稀疏索引、通配符索引（动态字段）——
它们的共同主题：**让索引只为"会被查询的文档/字段"存在**。

## 部分索引：只为需要的文档建索引

场景：订单集合 90% 已完成，查询永远带 `status: "ACTIVE"`——为全部
文档建 status 索引浪费 90%：

```javascript
db.orders.createIndex(
  { createdAt: 1 },
  { partialFilterExpression: { status: "ACTIVE" } }
)
```

- 索引体积与写放大**只覆盖被过滤的子集**——省空间省写成本；
- **硬约束**：查询条件必须与 partialFilterExpression **兼容**（包含
  该条件或其子集），否则不走该索引（优化器不会猜）；
- 与 MySQL 的差异：MySQL 无部分索引（可用"索引列+常量技巧"模拟）。

## 稀疏索引 vs 部分索引

- **稀疏索引**：只索引**该字段存在**的文档——`sparse: true`；
- **部分索引**：任意条件（字段存在是其中一种）——**部分是稀疏的
  超集**，新代码推荐 partialFilterExpression；
- 经典组合：**唯一 + 稀疏/部分**——允许多个"无该字段"的文档共存，
  但有字段的值必须唯一（如"可选邮箱必须唯一"）。

## 通配符索引：动态字段的救星

多态文档（不同商品不同属性：`attributes.color` / `attributes.size`）
——每个字段建索引不现实：

```javascript
db.products.createIndex({ "attributes.$**": 1 })
```

- **$** 索引自动覆盖所有子字段**——任意 attributes.xxx 的查询都能走；
- 代价：写放大（所有子字段都进索引）、不支持覆盖查询——**只索引
  真正会被查询的子树**（如 `attributes.$**` 而非 `$**`）。

## 高频追问速答

- **部分索引的查询为什么"猜不了"？** 优化器要求查询谓词**包含**
  索引的过滤条件——否则部分索引可能漏掉不在索引里的文档，结果
  就错了——这是正确性约束不是优化器偷懒。
- **text 索引和 ES 怎么选？** text 索引是轻量全文（单集合、简单
  分词），复杂检索/相关性/聚合上 ES（搜索篇）——轻量场景
  text 索引省一套基础设施。
- **索引这么多怎么治理？** `$indexStats` 看使用次数——零使用的
  索引删除（写放大白付）——与 MySQL 未使用索引治理同思路。

## 小结

- 部分索引 = 只索引谓词命中的子集（省空间省写，查询须兼容条件）；
  稀疏是它的字段存在特例。
- 通配符索引 = 多态文档的动态字段救星（注意写放大，只索引查询
  子树）。
- 索引治理同 MySQL：$indexStats 找零使用索引，删。
