团队从 MySQL 走向 PostgreSQL，或面试被问"两者怎么选"，都会卡在同一个地方：
**差异散落在无数细节里，没有一张地图**。本篇用 MySQL 视角立起 PG 的根基——
先抓四个底层差异，再谈选型；性能调优与集群篇（见高级/中级）都建立在这张图上。

## 进程模型：每连接一个进程

MySQL 是**一个服务进程 + 内部线程池**，每个连接一个线程；PostgreSQL 是
**每个连接 fork 一个独立后端进程**（backend process）。

- 直接后果：PG 的连接很"贵"（进程创建与内存开销），几百个连接就需要
  PgBouncer 之类的连接池做汇拢——这也是中级篇 pgpool 存在的理由之一。
- 隔离性更强：一个后端进程崩溃不影响其他连接（MySQL 线程崩溃可能拖累整个实例）。

## MVCC：元组多版本 vs undo log

这是两者**最核心**的差异，直接决定了运维话题的不同：

| | PostgreSQL | MySQL (InnoDB) |
| --- | --- | --- |
| 旧版本存哪 | 表内直接留旧元组（多版本共存） | undo log 单独存放 |
| 读旧版本 | 顺着元组链找可见版本 | 从 undo log 回溯重建 |
| 清理方式 | **VACUUM / autovacuum** 回收死元组 | purge 线程清理 undo |
| 典型问题 | **表膨胀**（清理跟不上写入） | 长事务拖住 purge、回滚慢 |

一句话：**PG 的 UPDATE 是"写新元组+留旧元组"**，旧元组要等 VACUUM 回收；
面试高频追问"为什么 PG 需要 autovacuum、表膨胀怎么来的"，答案全在这个模型里。
（本站 MySQL 事务篇讲过 InnoDB 侧，两相对照记得更牢。）

## 复制：物理 WAL vs 逻辑 binlog

- PG 的 **WAL（预写日志）是物理日志**——记录"哪个数据页哪个字节改了"。
  流复制（中级容灾篇的主角）把 WAL 流式发给备库重放，**备库与主库物理块级一致**。
- MySQL binlog 是**逻辑日志**（语句/行变更），除复制外还独立承担归档与
  数据恢复，配合 redo log 才是完整故事（见 MySQL 日志体系篇）。
- 差异的落点：PG 复制更"实"（级联、时间点恢复都基于 WAL），MySQL 生态里
  binlog 还要喂给 Canal 这类订阅工具——**PG 对应能力走逻辑复制槽**（10.0+）。

## 索引：PG 的类型是碾压项

MySQL (InnoDB) 实际只有 B+tree（和自适应哈希）；PG 内建一整个索引家族：

- **GIN**：倒排索引，JSONB、全文检索、数组字段的标配；
- **GiST**：地理空间（PostGIS 就建在它上面）、范围类型；
- **BRIN**：块级范围索引，时序大表的最小代价索引；
- **Hash / 部分索引 / 表达式索引**：按需创建，比如只给"未归档订单"建部分索引。

这就是"PG 更像数据库界的瑞士军刀"的底气——JSONB + GIN 可以让文档型需求
不引入 MongoDB 就落地（本站 MongoDB 方向的分片与复制集篇适合对照阅读）。

## 高频追问速答

- **count(*) 为什么 PG 慢？** MVCC 下每个会话可见性不同，count 必须**实时扫表**
  数可见行，MySQL InnoDB 同理但没有缓存层差异（PG 无查询缓存）——大表用
  估算（`pg_class.reltuples`）或计数表。
- **PG 为什么"没有"覆盖索引？** 有，11.0 的 INCLUDE 列；此前 PG 的 B-tree
  本来就会附带堆元组可见性信息，优化器更激进地走 Index Only Scan。
- **选型一句话**：复杂查询、GIS、JSONB 混合负载、数据完整性要求高 → PG；
  极简单行读写、生态与运维人才储备 → MySQL；两者如今都足够主流，
  团队熟悉度是权重最高的现实因素。

## 小结

- 四大差异：进程模型（连接贵 → 需连接池）、MVCC（元组多版本 → VACUUM/表膨胀）、
  复制（物理 WAL vs 逻辑 binlog）、索引（PG 家族碾压）。
- 用 MySQL 视角学 PG 最快的路径就是对着这张差异表逐行找体感——
  后续中级 pgpool 容灾、高级调优篇会反复回扣这里的 WAL 与 autovacuum。
