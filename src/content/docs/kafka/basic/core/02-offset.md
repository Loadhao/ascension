"消息丢了还是重复了"的排查，最后几乎都落到同一个词：**offset 提交时机**。
它也是 Rebalance 篇"重复消费来源"和幂等消费篇"至少一次"的公共根。本篇
把位移语义讲透——这是 Kafka 消费侧的最后一课基础。

## offset 是什么

每个分区是一条只追加的日志，**offset 就是消息在这条日志里的序号**
（0,1,2,…，架构篇的分段日志按起始 offset 命名）。单个分区内严格有序、
每个消息的 offset 唯一不变——"Kafka 只保证分区内有序"的物理基础就在这。

消费组的进度 = 组内每个分区"消费到了哪个 offset"，记在 Broker 端的
**`__consumer_offsets`** 内部主题里（不是存在消费者本地——组重平衡后
新成员要从 Broker 拿进度，这就是位移必须集中存储的原因）。

## 提交时机：丢失与重复的分水岭

消费者消费一批消息后，要把"我处理到哪了"提交上去。**先处理还是先提交**，
决定了故障时的表现：

| 顺序 | 故障表现 | 语义 |
| --- | --- | --- |
| 先处理，后提交 | 处理完没提交就崩溃 → 重启后**重新消费** | 至少一次（at-least-once） |
| 先提交，后处理 | 提交完还没处理就崩溃 → 重启后**跳过没处理的** | 至多一次（at-most-once） |

- 自动提交（`enable.auto.commit=true`，默认每 5 秒）：提交发生在 poll
  返回时——**既可能丢也可能重**，图省事但排查事故时是盲盒。
- 生产建议：`enable.auto.commit=false` + 处理完成后手动
  `commitSync()`（可靠，阻塞）/`commitAsync()`（异步，可能漏提交），
  常用组合是**异步提交 + 关闭前同步提交兜底**。

## "至少一次"不是免费的

先处理后提交保证了不丢，但**重复不可避免**（处理完、提交前崩溃，或
Rebalance 把分区转走）。这条链路串起了本站三篇的关系：

```
offset 语义（本篇）→ 至少一次 → 幂等消费三件套（可靠性篇）
→ Rebalance 加剧重复（Rebalance 篇）
```

面试标准句式："Kafka 保证 at-least-once，精确一次要靠幂等生产者 +
事务，消费侧的精确一次本质上要业务幂等或把 offset 与处理结果**原子提交**"
（如把 offset 存进处理结果的同一个数据库事务）。

## 高频追问速答

- **`__consumer_offsets` 为什么是 50 个分区？** 承载全集群所有消费组的
  提交流量，50 分区按组名哈希分摊——你消费组的 Coordinator 就是其中
  某个分区的 Leader 所在 Broker。
- **怎么重置位移重跑数据？** 消费组**必须先停**（有活跃成员则拒绝），
  `kafka-consumer-groups.sh --reset-offsets`：`--to-earliest` / `--to-datetime` /
  `--shift-by n`——修数据场景的标配。
- **提交的是"下一条"还是"最后一条"？** 提交的位移语义是"**下一条要读的
  offset**"——提交错一格就是丢一条或重一条，手写提交时最容易犯的边界错。

## 小结

- offset = 分区内序号，进度集中在 `__consumer_offsets`；分区内有序的根基。
- 提交时机决定语义：先处理后提交 = 至少一次（重复靠幂等兜），先提交后处理 =
  至多一次（可能丢）；自动提交是排查事故的盲盒，生产用手动。
- 位移与处理结果的原子性是消费侧"精确一次"的唯一正解，业务幂等是普适兜底。
