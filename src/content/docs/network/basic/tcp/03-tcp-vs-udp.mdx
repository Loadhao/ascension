## 差异矩阵（背这张表）

| 维度 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（三次握手） | 无连接，拿起就发 |
| 可靠性 | 确认 + 重传，不丢不重 | 尽力而为，可能丢/重/乱 |
| 有序性 | 按序交付 | 不保证顺序 |
| 数据形态 | **字节流**（无消息边界 → 粘拆包） | **数据报**（一次一发，天然有边界） |
| 头开销 | 20~60 字节 | 固定 8 字节 |
| 收发模型 | 一对一 | 一对一/一对多（广播/组播） |
| 拥塞控制 | 有（为网络着想） | 无（自己冲） |

UDP 不是"残缺的 TCP"，是**故意做减法**：把可靠性、流控全部上交
应用层，换取极低延迟与极简头部。

## 各自的主场

| TCP | UDP |
|---|---|
| HTTP/1.x、HTTP/2、SSH、数据库连接、文件传输 | DNS 查询、DHCP、NTP、SNMP |
| 要"一个字节都不能错、按序"的业务 | 要"快、单次问答可容忍丢失"的交互 |
| 长连接服务（IM 推送常在 TCP 上自建协议） | 音视频流（丢一帧无所谓，卡 100ms 才致命）、游戏同步 |

选型一句话：** correctness 优先选 TCP，latency 优先选 UDP；UDP 的
可靠性按需在应用层自建**。

## UDP 上的"重新发明 TCP"

现代协议大量在 UDP 上自建可靠层，取两者之长：

- **QUIC（HTTP/3 的底座）**：UDP 之上实现可靠 + 有序 + 拥塞控制，
  还带 0-RTT 建连与连接迁移（换 Wi-Fi 不断线）——TCP 做不到的
  三件事全补齐了（见[HTTP 演进](/network/basic/http/03-http-evolution/)）。
- **KCP / WebRTC（SRTP）**：游戏与音视频自选"部分可靠"——旧数据
  宁可丢也不重传堵路。**可靠性是谱系，不是开关**。
- 内网 RPC 也常自研 UDP 协议：握手省一个 RTT，超时重传自己做。

## 常见追问

- **UDP 会粘包吗？** 不会——每次 `sendto` 就是一个独立 datagram，
  边界天然存在；但会**丢包、乱序、分片**（超过 MTU 在 IP 层分片，
  一片全丢整包废）。
- **TCP 有消息边界吗？** 没有，靠应用层定义（[粘包拆包](/java/basic/io/03-tcp-sticky-packets/)）。
- **为什么 DNS 选 UDP？** 一问一答、报文小、重传自己做足够了——
  握手的 RTT 都省下（见[DNS](/network/basic/foundation/02-dns/)）。

## 小结

- TCP 买的是可靠有序字节流（贵在握手/重传/流控），UDP 买的是便宜
  快捷有边界（代价是自己兜底）。
- 场景分水岭：错不起 vs 等不起；QUIC/KCP 证明"可靠性可以在 UDP
  上按需重建"。
- 对比题落到四个关键词：连接、可靠、有序、边界。
