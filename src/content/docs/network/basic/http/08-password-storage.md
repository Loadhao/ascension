"数据库泄露了，用户密码会怎样？"——答案取决于你当年怎么存的密码。
**明文和 MD5 都是事故预备役**。密码存储是安全类面试的入场题：成本极低
的几个决策，决定泄露时的灾难等级。

## 为什么 MD5 存密码必死

MD5 作为密码哈希有两大死穴：

1. **太快**：现代 GPU 一秒能算上百亿次 MD5——泄露的库可以离线高速穷举，
   弱密码秒破；
2. **可预计算**：全网常用密码的 MD5 早被做成**彩虹表**（明文↔哈希对照表），
   查表即还原。

SHA-256 也一样快、一样能被彩虹表覆盖——**"换个哈希算法"不是解药，
密码哈希需要的是"故意很慢"的算法**。

## 正确姿势：慢哈希 + 盐

| 手段 | 解决什么 | 原理 |
| --- | --- | --- |
| 加盐（salt） | 彩虹表 | 每用户随机串拼进密码再哈希——相同密码哈希也不同，预计算表全部失效 |
| 慢哈希（bcrypt/argon2） | 离线穷举 | 故意设计得慢/费内存（cost factor），单次几十毫秒——GPU 穷举成本暴涨 |
| 自带盐（bcrypt 推荐） | 实现出错 | salt 嵌在结果串里，不用自己存第二列 |

```text
存储的形态：$2b$12$<salt+hash>   ← bcrypt：算法版本、成本因子、盐、哈希一体
```

- **为什么故意慢**：正常登录一天几十次毫秒级无感；攻击者离线爆破一个
  密码要几十毫秒 × 上亿次——成本差出十几个数量级；
- **argon2** 是更新一代（抗 GPU/内存优化，2015 密码哈希竞赛冠军），
  bcrypt 最普及，两者都合格；**永远不要自研哈希方案**。

## 传输与流程的安全纪律

- **HTTPS 是前提**：明文 HTTP 上讨论密码安全没有意义（登录态篇的 Cookie
  安全同样以 HTTPS 为前提）；
- **前端先 MD5 再传 = 自欺欺人**：攻击者拿到 md5(密码) 后直接重放这个
  哈希即可登录（哈希成了新密码），且彩虹表同样覆盖——传输保护交给
  HTTPS，服务端自己慢哈希；
- **不要在 URL 里放密码/token**：URL 会进访问日志、代理日志、浏览器历史；
- **登录失败提示模糊化**："用户名或密码错误"——分开提示等于帮攻击者
  确认账号存在；
- **限流与锁定**：登录接口按 IP+账号限流，防在线爆破（见分布式限流篇）。

## 高频追问速答

- **加盐了为什么还要慢哈希？** 盐防的是预计算（彩虹表），慢哈希防的是
  现场穷举——泄露后的爆破没有彩虹表可查，攻击者直接暴力算，慢哈希
  抬高单次成本。
- **数据库泄露后除了密码还怕什么？** 撞库——用户在别处复用同密码；
  所以要强制重置 + 通知用户改其他站点密码，这是"加密盐也救不了"
  的习惯问题。
- **JWT 场景密码存哪？** 无论 Session 还是 JWT，认证后服务端都不该长期
  持有明文/可逆密码——JWT 只放身份声明，密码只用于登录时刻校验。

## 小结

- 密码存储三件套：**慢哈希算法（bcrypt/argon2）+ 每用户随机盐 + HTTPS
  传输**；MD5/SHA-256 直接存密码都是事故。
- 慢哈希抬高离线爆破成本，盐废掉彩虹表，两者缺一不可。
- 流程纪律：URL 不放凭证、失败提示模糊化、登录接口限流。
