搜索框每敲一个字就弹出 TopN 联想词，延迟要求 **50ms 级**——这是把
前缀匹配、排序和缓存压到极限的场景。与敏感词过滤篇同源（都是 trie），
但多了一个"按热度排序"的维度，工程形态完全不同。

## 从 LIKE 的灾难说起

`SELECT word FROM words WHERE word LIKE '苹果%'`——前缀索引能救"前缀
匹配"，但救不了：

- 每敲一个字打一次 DB，QPS 是搜索主链路的几十倍（每个字符都触发）；
- **没有热度排序**——联想的价值恰恰是"大家都在搜什么"排前面；
- 无法做拼音、纠错这类变体。

联想服务的正确形态：**内存级前缀索引 + 热度权重 + 多级缓存**。

## 两种内存索引：trie 与 FST

| | trie（前缀树） | FST（Finite State Transducer） |
| --- | --- | --- |
| 结构 | 逐字符分支 | 共享前后缀的有限状态机 |
| 内存 | 前缀共享，仍偏大 | **极省**（Lucene 用它做前缀索引） |
| 排序支持 | 节点挂 topN 即可 | 原生支持按权重输出 |
| 工程载体 | 自研/Redis | **ES completion suggester** |

- 敏感词篇的 trie 是"判断有没有"，联想的 trie/FST 还要**带权重输出
  TopN**——每个前缀节点维护"该前缀下热度最高的 N 个词"；
- ES 的 completion suggester 底层是 FST：前缀查找 O(前缀长)，内存
  友好，生产首选（不用自己造 trie）。

## 排序：热度 + 个人化

联想词的价值排序 = **全局热度 × 个人化修正**：

- **全局热度**：历史搜索次数（滑动窗口，防止老热词霸榜）+ 商品销量加权；
- **个人化**：用户自己的搜索历史、已购买品牌优先——两个分数加权融合
  后再取 TopN；
- 热词榜（实时热搜）单独维护：滑动窗口计数（Redis zset，按时间窗衰减），
  与前缀索引解耦。

## 数据与更新：词从哪来

1. **基础词表**：商品名/品牌/类目/同义词，定时全量重建 FST（分钟级）；
2. **实时热词**：搜索日志实时聚合，热词写入单独的 Redis zset，查询时
   与 FST 结果合并——**全量重建保正确，实时层保新鲜**；
3. 新品上架自动进词表（数据管道驱动，不靠人工维护）。

## 高频追问速答

- **拼音联想怎么做？** 词表构建时预生成拼音形式（全拼/首字母）一起入
  FST，查询串先尝试原文再尝试拼音——多一份索引换体验，归一化思想与
  敏感词篇的变体处理一致。
- **用户打错字怎么办？** 纠错是另一条链路：编辑距离（1~2 位内）在词典里
  找最近词，或用embedding 语义近似——先联想后纠错，两级兜底。
- **为什么不用 Redis 的 zset 存全部前缀？** 前缀组合是词数的量级爆炸
  （"苹果手机"产生 4 个前缀键），存储成本失控；FST 共享前后缀才是
  正解——Redis zset 适合存"实时热词榜"这一小层。

## 小结

- 联想 = 内存前缀索引（trie/FST，生产用 ES completion）+ 热度加权 +
  多级缓存，LIKE 方案在延迟与排序上双输。
- 排序 = 全局热度（滑动窗口）× 个人化修正；词表全量重建 + 实时热词
  两层结合。
- 拼音与纠错是"归一化 + 多索引"的变体处理——与敏感词篇同源不同用。
