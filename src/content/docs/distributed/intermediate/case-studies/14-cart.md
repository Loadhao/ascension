购物车是电商的"常驻内存区"：**读多写多、未登录也能用、多端要同步**。
它不像秒杀那样有瞬时洪峰，却有三个自己的坑：游客态怎么存、登录怎么
合并、失效商品怎么标——电商面试里它是优惠券的固定搭档题。

## 存储结构：Redis hash 为主，DB 异步持久

```text
cart:{uid} = Hash { skuId: 数量, ... }
```

- **Redis hash 为主存储**：加购/改数量/删除都是 HINCRBY/HDEL 单字段
  操作，天然按用户隔离，无锁冲突；
- **DB 异步持久**：购物车丢了很恼火但不致命——Redis 为主 + MQ 异步
  落库（用户券那种"必达"等级不需要）；
- **商品上限**（如 120 个 SKU）：hash 字段数控制——不加限制的购物车
  是大 key 治理篇的常客。

## 游客态与登录合并：冲突策略是灵魂

未登录用户用 cookie/localStorage（或临时游客 ID 的 Redis hash）记
购物车，登录时要**合并**——两份购物车可能有同一个商品：

- **同商品冲突**：数量**取大**（用户意图"想要更多"）或相加封顶——
  相加更符合直觉，取大更保守，按业务定但要说清理由；
- **合并时机**：登录成功响应里返回合并后结果，一次性写回 Redis，
  清游客态；
- 合并操作要幂等（前端重复触发登录回调时不能叠加数量）——以"游客态
  清空"作为合并完成的标志。

## 失效与价格：展示层永远实时校验

购物车里的商品在结算前可能：下架、改价、库存清零。**购物车只存
skuId + 数量，不存价格快照**——展示与结算时实时查商品服务：

- 失效商品**置灰不可结算**而非直接删除（用户可能想留着等补货）；
- 结算时二次校验价格与库存——以结算页为准，购物车页的价格只是参考
  （防止"购物车 9.9 结算 99.9"的资损事故）。

## 高频追问速答

- **为什么用 hash 不用 string 存 JSON？** hash 的字段级操作（改一个
  SKU 数量）不用读改写整个购物车，并发改不同字段互不覆盖。
- **购物车上限为什么必须有？** 用户侧是无意义堆积（认知负担），系统侧
  是 hash 膨胀成 big key——120 上限 + 淘汰最久未动是常见做法。
- **加购和直接购买的区别？** 直接购买走独立结算链路（单 SKU、数量
  校验更严），不进购物车——两条链路的库存扣减时机可以不同。

## 小结

- Redis hash 按用户隔离，字段级操作无锁冲突；DB 异步持久即可，
  购物车不需要必达。
- 游客态合并的灵魂是**冲突策略**（相加封顶/取大）+ 合并幂等。
- 不存价格快照，结算实时校验；失效置灰不删除；上限治理防 big key。
