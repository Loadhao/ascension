"订单列表谁都能打开，但普通员工只能看自己的、主管看本部门、总监看
全部"——**功能权限管"能不能访问这个接口"，数据权限管"返回哪些行"**。
中后台系统必备，也是权限体系从"按钮级"深入到"行级"的必考题。

## 两层权限，别混为一谈

| | 功能权限 | 数据权限 |
| --- | --- | --- |
| 管什么 | 能否访问接口/菜单/按钮 | 同接口返回哪些行 |
| 粒度 | 资源级（订单管理） | 行级/列级（谁的订单） |
| 实现 | RBAC（角色-资源） | RBAC + **数据范围**（角色-范围） |

数据范围四档经典设计：**全部 / 本部门及以下 / 仅本部门 / 仅本人**——
挂在角色上，一个用户多角色时取并集（可见范围最大的）。

## 实现：SQL 注入式拼接（拦截器）

主流做法是**MyBatis/JPA 拦截器自动改写 SQL**——业务代码完全不感知：

```mermaid

    B["业务代码<br/>SELECT * FROM orders"] --> I["数据权限拦截器<br/>解析表 → 注入范围条件"]
    I --> S["改写后 SQL<br/>... AND dept_id IN (可见部门)"]
    S --> DB["数据库执行"]

    classDef hl stroke-width:1.5px
```

- 拦截器根据当前用户的数据范围生成过滤片段拼进 WHERE——业务开发
  零侵入，漏拼的 SQL 在别处写就绕过了权限（**统一入口是安全前提**）；
- 跨服务/微服务场景：数据范围作为用户上下文透传（登录态篇的
  JWT Payload 或请求头），下游服务同样拼接。

## 部门树："本部门及以下"怎么查

数据范围的难点在**组织树**——"本部门及以下"要拿到子树所有部门 ID：

- **path 路径法**：部门表存 `path = /1/5/12/`，查子树 = `LIKE '/1/5/%'`
  ——简单高效（前缀索引），层级变更要重刷子树 path；
- **闭包表**：所有祖先-后代对存表——查询最快，维护成本高；
- 递归 CTE（`WITH RECURSIVE`）：MySQL 8/PG 原生支持——不用预计算，
  深树性能看情况。

## 性能：数据权限对索引的影响

注入的过滤条件**必须能走索引**：`dept_id`/`user_id` 要在建复合索引里
（如 `idx_dept_status_created(dept_id, status, created_at)`）；否则
权限过滤变成全表过滤，大表直接慢查询——**数据权限不是纯功能需求，
也是查询性能需求**。

## 高频追问速答

- **数据权限和功能权限的实现可以共用 RBAC 吗？** 共用角色模型，
  数据范围作为角色的附加维度——角色既决定能干什么，也决定能看多大。
- **拦截器改写 SQL 有什么坑？** 复杂 SQL（子查询/JOIN 多表/UNION）
  的解析改写容易出错；敏感报表 SQL 直接绕过拦截器——**边界 SQL
  白名单 + 代码评审**是配套纪律。
- **数据库原生方案？** PG 的 RLS（Row Level Security）把过滤下沉到
  库层——更彻底但运维与调试成本高，国内中后台多用应用层拦截器。

## 小结

- 功能权限与数据权限是两层：RBAC + 数据范围四档（全部/部门及以下/
  本部门/本人），多角色取并集。
- 实现：拦截器 SQL 注入（零侵入）+ 统一入口防绕过；组织树用 path
  法查子树。
- 数据范围条件必须进索引——**数据权限同时是性能需求**。
