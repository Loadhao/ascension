点赞看似一个"加一"按钮，系统设计的完整答案要回答**三个子问题**：
是否点过（去重）、点了多少（计数）、谁点过我（列表）——三问的存储选型
各不相同，选错就是事故。社交类面试的入场级场景题。

## 三问拆解与存储选型

| 子问题 | 需求特征 | 推荐结构 |
| --- | --- | --- |
| 是否点过 | 布尔判断，量巨大 | Set（精确）/ bitmap（稠密+有序时） |
| 点了多少 | 计数，读多写多 | 计数器（Redis INCR）+ 异步落库 |
| 谁点过我 | 列表 + 可能分页 | zset（按时间排序，得分=时间戳） |

```bash
SADD like:{contentId} uid            # 去重：返回 0 = 已点过
INCR like:count:{contentId}          # 计数
ZADD liked:{uid} <timestamp> contentId   # 我点赞的内容（按时间排）
```

## 写路径：先去重，再计数，最后落库

点赞是**高频写 + 允许短暂延迟一致**的典型：

1. **去重**：SADD 判断是否点过（点过直接返回，幂等）；
2. **计数**：Redis INCR（或取消时 DECR）——展示层读这个数；
3. **落库异步**：点赞记录发 MQ 异步写关系库（明细用于风控/分析），
   计数定期与库对账校准。

取消点赞是逆操作（SREM/DECR），**幂等性靠 Set 天然保证**——重复取消
无副作用，这比"计数扣减到负数要防御"的裸计数器方案稳得多。

## 热点内容的两道坎

- **热 key**：爆款内容的 `like:count:{id}` 被百万 QPS 打——本地缓存
  计数（应用内存聚合后定期同步 Redis）+ Redis 集群分片（热 key 治理篇）；
- **大 V 的百万赞列表**：zset 单 key 过大——**计数与列表分离**：列表只
  存"最近 N 条"（分页场景够用），更早的走归档/游标；全量去重集合对
  大 V 换 bitmap（uid 稠密时）或布隆过滤器（允许极低误判时）。

## 高频追问速答

- **计数用 Redis 还是直接写库？** 直接 UPDATE 计数列 = 热点行锁竞争
  （同红包热点账户问题）；Redis 内存计数 + 异步批量合并写库是标准解。
- **Set 和 bitmap 怎么选？** uid 稠密且上限明确（如帖子维度 uid < 1 亿）
  → bitmap 省 8 倍；uid 稀疏 → Set。先算两边的内存账再选。
- **点赞和收藏的区别？** 收藏无公共计数诉求但**列表必须完整可靠**
  （用户找得到），落库从"异步可容忍"升级为"同步必达"——同一套结构，
  一致性等级不同。

## 小结

- 三问三结构：去重用 Set/bitmap，计数用 INCR + 异步落库，列表用
  zset 按时间排序。
- 热点与大 V 是两条演进线：本地缓存聚合计数、列表截断 + 去重集合换型。
- 点赞允许最终一致，收藏要必达——同一按钮，一致性等级由业务定。
