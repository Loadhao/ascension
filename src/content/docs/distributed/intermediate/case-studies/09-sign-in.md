签到功能看似简单：每天记一次"来过"。但"1 亿用户 × 每天一条记录"的朴素
方案会快速吃掉数据库；**位图（bitmap）方案把它压缩到每用户每月 4 字节**，
是"选对数据结构解决存储与统计"的教科书案例。

## 朴素方案的账

按关系库思路：`sign(uid, date)` 一天一行——1 亿用户 × 365 天 = 365 亿行，
而每行的信息量只有 1 bit（签/没签）。**存储密度 1/8 的字节单位都占不满**，
查询"某月签到天数"还要按 uid 聚合扫描。

## 位图方案：一天一位

Redis 的 bitmap（本质是 String 的位操作）：**key 按用户+月份，offset 是
日期-1**：

```
SETBIT uid:sign:202609 8 1        # 9 号签到（offset = 8）
GETBIT uid:sign:202609 8          # 查某天
BITCOUNT uid:sign:202609          # 本月签到总天数
BITPOS uid:sign:202609 1          # 第一个签到日（从左找第一个 1）
```

- 容量：31 天 = 31 bit ≈ **4 字节/用户/月**，1 亿用户每月约 400 MB
  （对比关系库方案几个数量级的差距）；
- 连续签到：从"今天"往回找连续的 1（`BITPOS` 配合位段读取或客户端
  按字节取回后位运算）；
- **跨月边界**：key 按月切分，"连续签到"在月初要拼接上月尾部——
  客户端取两个月 key 合并计算。

## 补签与业务规则

- **补签**：`SETBIT` 重写指定位 + 校验补签卡次数（另一结构计数）——
  补签让位图失去"只追加"的简单性，需要记录补签流水；
- **月度奖品**：BITCOUNT 达标发奖，用"月度达标记录"结构防重复发放；
- **重置与归档**：跨年后上月 key 归冷，按需归档（bitmap 是连续字节，
  导出即压缩——冷数据几乎零成本）。

## 亿级用户的工程细节

- **key 设计**：`uid:sign:yyyyMM` 而不是 `sign:yyyyMM:uid` 大 key——
  单 key 控制在 4 字节量级，避免大 key（对照 Redis 大 key 治理篇）；
- **签到接口**：SETBIT 天然幂等（重复签到同一位仍是 1），无需额外去重
  ——数据结构本身消解了并发问题；
- **统计类需求**：全站"今日签到人数"用另一个 bitmap（按天、offset=uid
  分段或 HyperLogLog 按精度选）——**不同问题用不同的位图**。

## 高频追问速答

- **bitmap 为什么这么省？** 一个 bit 表达一个布尔事实，且按时间天然稠密
  排列——**布尔 + 稠密 + 有序**三个条件都满足才是 bitmap 的主场
  （稀疏场景该用 Set）。
- **亿级用户怎么分片？** 按 uid 哈希到多个 Redis 实例；跨实例统计用
  各实例 BITCOUNT 汇总——避免单实例大 key 与热压力。
- **位图还能干嘛？** 在线状态、点赞去重（粗粒度）、特征标记集合——
  本质都是"对象 × 布尔位"矩阵。

## 小结

- 位图把签到从"365 亿行"压到"每月 4 字节"，SETBIT/GETBIT/BITCOUNT/
  BITPOS 覆盖全部操作。
- 选型前提是**布尔 + 稠密 + 有序**；补签/跨月是工程细节，key 按
  用户+月拆分避免大 key。
- 签到、在线状态、去重标记——同一个位图思想的不同业务皮。
