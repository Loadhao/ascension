评论系统是 UGC 应用的标配（文章/视频/商品），也是"看起来简单、做深了
全是细节"的场景：**无限嵌套的回复怎么建模、分页怎么分、热评怎么排、
计数怎么不乱**。与点赞篇、敏感词篇是一套组合。

## 数据模型：两级拍平，不做无限递归

产品形态通常是"评论 + 回复"两级，但回复可以互相回复（@某人）。经典
建模是**两级拍平**：所有回复都直接挂在根评论下，用 `root_id` 归组 +
`parent_id`/`reply_to_user` 保留回复对象：

```text
comment: id, root_id, parent_id, reply_to_user, content, like_count...
根评论 A（root_id = 自身 id）
├─ 回复 B（root_id = A，reply_to_user = null）   ← 直接回复 A
├─ 回复 C（root_id = A，reply_to_user = B）      ← 回复 B，但仍拍平挂 A
└─ 回复 D（root_id = A，...）
```

- **为什么不做无限树**：递归查询/渲染复杂、分页困难——产品上"回复谁"
  用 @用户名 表达，结构上永远两级，**分页语义清晰**（每个根评论下
  回复数可数）；
- 删除用**标记删**：根评论删除时子回复"挂空"处理（显示"已删除"或
  隐藏整楼），业务定。

## 分页：根评论游标分页 + 回复折叠

- **根评论列表**：游标分页（按热度分/时间，`WHERE root_id IS NULL AND
  cursor < ? LIMIT 20`——深分页问题见 ES 分页篇同源逻辑）；
- **每条根评论**：只带前 2~3 条回复 + "共 N 条回复，展开查看"——
  展开时再按游标拉该根下的回复；
- 这就是"前 N 条 + 懒加载"的**折叠模式**：首屏轻、体验顺。

## 热评排序：热度分的两种算法

- **朴素**：点赞数排序——老热评永远霸榜，新内容没机会；
- **时间衰减**：`score = (点赞数 + 1) / (age_hours + 2)^ gravity`
  （Hacker News 式）——新评论有时间红利；或滑动窗口点赞数（近 24h）
  ——与搜索联想篇的热词衰减同思想；
- 热度分**预计算**（定时/事件驱动更新 score 字段）而不是查询时算
  ——排序字段落库，查询走索引。

## 计数与联动

- 评论数/点赞数：计数器异步累加（点赞篇同款），定时对账校准；
- 发评前置检查：敏感词过滤（case-studies 篇互链）+ 频控 + 登录态；
- 高频追问"评论数和实际对不上"：计数器与明细漂移——对账任务修复，
  与所有计数系统的最终一致纪律相同。

## 高频追问速答

- **回复可以无限嵌套吗？** 数据上可以（parent_id 链），产品上拍平两级
  ——无限嵌套的 UI 和查询都是灾难，@提及 表达回复对象足够。
- **热评和最新两个 Tab 怎么支持？** 同一份数据两个排序字段（score 与
  created_at 各自索引），游标分页各自游——排序字段落库 + 索引。
- **评论先审后发还是先发后审？** 先审后发（延迟可见）防违规扩散；
  先发后审配秒级敏感词 + 举报降权——风控等级决定，两方案都要留
  人工复审入口。

## 小结

- 两级拍平 + root_id 归组是评论建模的标准答案——无限树是自找麻烦。
- 分页：根评论游标分页 + 回复折叠懒加载；排序：热度分预计算落库。
- 与点赞（计数）、敏感词（前置过滤）同属一套 UGC 组合件。
