## 为什么需要框架

设计题（"设计一个秒杀/短链/朋友圈"）没有标准答案，考察的是
**拆解能力与权衡意识**。没有框架的回答容易变成技术名词堆砌——
先说 Redis 再说 MQ，每样都对，整体不及格。六步框架让任何设计题
都有稳定的起手式：

```mermaid

    S1["① 需求澄清<br/>先问再答"] --> S2["② 容量估算<br/>数字定架构"]
    S2 --> S3["③ 数据模型<br/>接口与存储"]
    S3 --> S4["④ 核心链路<br/>写路径/读路径"]
    S4 --> S5["⑤ 规模化<br/>瓶颈→手段"]
    S5 --> S6["⑥ 容错权衡<br/>说出代价"]
```

## ① 需求澄清：先问再答

拿到题**不要立刻设计**，先花两分钟收敛边界：

- 功能边界：做"核心闭环"还是全功能？（短链要不要后台管理？）
- 非功能指标：QPS 量级、数据量、读写比、一致性要求、延迟要求。
- 明确说出"假设"：移动端为主？国内还是全球？

**面试官想听什么**：工程师在动手前先对齐问题——这一步的提问
质量直接定档。

## ② 容量估算：数字决定架构

用[容量规划](/distributed/intermediate/performance/03-capacity-planning/)
的方法现场估算：日活 × 操作次数 → QPS → 峰值 → 存储量 × 保留
期限 → 带宽。数量级决定选型：

| 量级 | 架构暗示 |
|---|---|
| QPS 100 | 单库单表都够，别过度设计 |
| QPS 1万 | 缓存 + 读写分离 |
| QPS 10万+ | 分片、多级缓存、异步化全上场 |
| 存储 TB/天 | 冷热分层 + 归档 |

**雷区**：跳过估算直接选"高并发全家桶"——面试官会追问"你这个
QPS 需要吗"。

## ③ 数据模型：接口草图 + 存储选型

- 核心实体两三个就够（短链：url_mapping(code, long_url, 状态)），
  画出主键、索引、唯一约束。
- 存储选型说理由：强一致事务 → MySQL；海量读 + 灵活 schema →
  文档/宽表；关系复杂 → 图；全文检索 → ES（选型依据见
  [MQ 选型同类思路](/middleware/basic/mq/02-mq-comparison/)）。

## ④ 核心链路：把写路径和读路径画出来

用一张图讲清"一次请求怎么流"：秒杀的写路径（限流 → 预扣 →
MQ → 落库）、短链的读路径（缓存 → DB → 302）。**先画 happy
path，异常分支留到第⑥步**——顺序反了会陷入细节出不来。

## ⑤ 规模化：每个瓶颈对应一个手段

主动问自己"哪个环节先崩"，瓶颈→手段的标准映射：

| 瓶颈 | 手段 |
|---|---|
| 读放大 | 多级缓存、CDN（击穿/穿透预案） |
| 写洪峰 | MQ 削峰、批量合并 |
| 数据量大 | 分库分表、冷热分离、归档 |
| 单点 | 冗余 + 故障转移（选主/哨兵） |
| 跨机房 | 多活/单元化、就近接入 |

## ⑥ 容错与权衡：说出代价是最高分

每个设计选择都配一句"代价是什么"：

- 上缓存 → 接受不一致窗口，配双写一致性方案。
- 上 MQ → 接受延迟与重复消费，配幂等。
- 最终一致 → 说明对账兜底。

再加两样收尾：**监控告警**（怎么知道它坏了，引用三支柱）与
**演进路线**（"如果 QPS 再涨 10 倍，下一步拆什么"）——展示
架构是演进而来，不是一次到位。

## 雷区与加分项

| 雷区 ❌ | 加分 ✅ |
|---|---|
| 不问需求直接画图 | 先澄清边界、声明假设 |
| 没有数字就堆中间件 | 用估算约束选型 |
| 只讲 happy path | 主动讲故障场景与降级 |
| 一步到位"微服务全家桶" | 给出从小到大的演进路线 |
| 选择不提代价 | 每个取舍配一句 trade-off |

## 用三道真题验证框架

- [秒杀](/distributed/intermediate/case-studies/01-flash-sale/)：估算（百万 QPS）→ 链路（层层收窄）→ 权衡（Redis 预扣换性能，对账保正确）。
- [短链](/distributed/intermediate/case-studies/02-short-url/)：估算（读多写少）→ 模型（发号器）→ 权衡（302 换统计能力）。
- [Feed 流](/distributed/intermediate/case-studies/03-feed-stream/)：瓶颈（大 V 写扩散爆炸）→ 混合策略 → 权衡（复杂度换读写均衡）。

## 小结

- 六步框架：澄清 → 估算 → 模型 → 链路 → 规模化 → 容错权衡，
  每步都有"面试官想听什么"。
- 估算定选型、链路先 happy path、权衡必带代价——三条纪律区分
  及格与优秀。
- 设计题答的是"演进能力"：给出下一步，比给出终态更显功力。
