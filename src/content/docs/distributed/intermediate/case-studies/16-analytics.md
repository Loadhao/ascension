"用户点了哪个按钮、页面停留多久、转化漏斗在哪一步断了"——产品决策的
数据来自埋点上报。它是个**反向的高并发写入系统**：峰值不可控、单条数据
价值低（丢几条没关系）、但 schema 会持续演进——设计约束与订单系统
正好相反。

## 上报端：批量、延迟、失败容忍

前端/客户端埋点的核心矛盾：**事件高频产生 vs 不能每个事件一个请求**。

- **本地队列 + 批量合并**：事件先进内存队列，凑满 N 条或到时间窗
  （如 5s/20 条）批量上报——HTTP 请求数降一个数量级；
- **时机选择**：`sendBeacon`（页面卸载也能发，不阻塞关闭）、空闲时上报、
  首屏数据延后——埋点不能影响业务体验；
- **失败容忍**：上报失败**不无限重试**——本地缓存有限，超限丢最旧的
  （埋点丢 1% 无感，订单丢 1% 是事故——**容忍度决定架构**，
  与订单系统的"必达"完全相反）。

## 服务端：削峰、幂等与 Schema 演进

- **接入层削峰**：埋点峰值不可控（运营活动、明星事件），接入层用
  消息队列缓冲 + 批量入库（Kafka→消费端批量写），天然抗洪峰；
- **幂等**：事件带 eventId（客户端 uuid），消费端按 eventId 去重
  ——重试与重传导致的重复在入口挡掉（幂等篇的唯一索引武器）；
- **Schema 演进**：埋点字段会不断加——事件用**宽表 JSON 列**或
  "事件名+属性 JSON"模式，避免每加一个字段就改表结构；
  消费端对未知字段忽略（结构化输出篇的向前兼容同理）。

## 从采集到分析：完整链路

- 分析查询是**扫描聚合型**（漏斗/留存/路径），OLAP 引擎才是对的工具
  ——别把分析查询打到业务库（可观测性三支柱篇的指标/日志同理）；
- **数据质量**：丢数据、重复、乱序（客户端时钟）在清洗端归一——
  埋点的"准确"是统计意义上的准确。

## 高频追问速答

- **埋点丢了怎么办？** 分级：核心漏斗事件（下单/支付）可以走强一致通道
  重试；行为明细允许丢——**按事件价值分级**，别用订单的标准要求埋点。
- **客户端时钟不准，事件时间怎么定？** 服务端接收时间为准 + 客户端
  事件时间仅作参考——乱序在清洗端按接收序归一。
- **实时看板怎么做？** 链路末端分两层：批量入 OLAP（分钟级）+
  热点指标走流式聚合（Flink/Redis 计数器）——实时是加价选项，
  不是默认要求。

## 小结

- 埋点系统 = 本地批量上报 + 接入层削峰幂等 + MQ 缓冲 + OLAP 分析
  ——**容忍丢数据**是它与订单系统最本质的架构差异。
- Schema 演进用宽表/JSON 列 + 向前兼容，别让埋点需求拖垮表结构。
- 链路上每层都在做同一件事：**把不可控的洪峰变成可控的批量**。
