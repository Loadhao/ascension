请假审批、报销审批、合同会签——审批流是中后台系统的标配，也是**状态机
复杂度的天花板**：多级审批、条件路由（金额大要加财务会签）、驳回回退、
动态加签——用硬编码 if 写的人，最后都在重写一个工作流引擎。

## 朴素方案的崩溃点

`status` 字段 + if/else：待主管审批 → 待经理审批 → 通过。崩溃于：

- **条件路由**：金额 > 5000 要加财务节点、部门不同审批人不同——if
  分支爆炸；
- **驳回**：驳回到发起人、驳回到上一节点、驳回到指定节点——每种都改
  if 逻辑；
- **动态调整**：加签/转办/委托（审批人休假）——硬编码彻底崩溃。

崩溃的本质：**审批流的"流程定义"和"流程实例"应该是数据，不是代码**。

## 两个层次的方案

### 层次一：单链状态机（≤3 级固定审批够用）

审批单表 + 审批节点实例表（预生成整条链）：

```text
approval: id, biz_type, biz_id, status(进行中/通过/驳回/撤销)
approval_node: id, approval_id, node_order, approver, status(待处理/通过/驳回/跳过)
```

- 推进 = 当前节点通过 → 下一节点置待处理；驳回 = 状态置驳回 + 记录
  回退目标；**节点链是数据**（下单时按规则生成），加条件路由只是改
  生成规则——比 if/else 已前进一大步；
- 短板：**并行会签**（多节点同时审、全部通过才过）和复杂网关支持不了。

### 层次二：工作流引擎（Flowable/Camunda）

用 BPMN 描述流程：节点（用户任务/服务任务）、**网关**（排他网关做条件
路由、并行网关做会签）、变量（金额/部门驱动路由）、历史表全记录：

- 加签/转办/委托/撤回是引擎内置能力；
- 代价：学习成本、表结构重量、排障复杂度——**引入引擎是架构决策不是
  引依赖**（对照落地选型篇的"最后才上重武器"）。

分界线经验：**≤5 个固定节点、无线性化需求 → 状态机；动态流程/会签/
多业务线复用 → 引擎**。

## 驳回与加签：两道设计必答题

- **驳回回退到哪？** 三种语义：回到发起人（重新提交走全链）、回到上一
  节点（局部修正）、指定节点——节点实例表里记录"回退目标"字段，
  配置期决定；
- **动态加签**：审批人觉得需要拉更多人——在当前节点后**插入临时节点**
  （节点实例表天然支持插入），类型分"会签前加签/后加签"——引擎有
  原生支持，状态机要自己设计插入逻辑。

## 高频追问速答

- **审批人离职/转岗怎么办？** 审批人建模用"角色/岗位"而非具体人，
  人员变动只改映射；进行中的单据支持转办（改节点 approver + 留痕）。
- **审批超时怎么办？** 节点实例带超时时间，超时自动提醒/自动通过/
  自动升级——延迟任务（订单超时篇）的审批版。
- **怎么防止审批记录被篡改？** 流转记录只追加（append-only）+ 关键
  操作审计（chattr +a 的日志保护思路同源）。

## 小结

- 流程定义与实例数据化是审批流的分水岭：状态机管固定短链，引擎管
  动态与会签。
- 驳回目标、动态加签、审批人抽象是三道设计必答题，答不好就是返工。
- 何时上引擎与何时上微服务同类：**先让复杂度真实存在，再引入重武器**。
