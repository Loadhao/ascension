## 先想清楚：优化之前，先看耗时地图

优化接口的第一课不是技巧，是**量级感**——不同操作耗时差着数量级，
找准最贵的那一段下手，效果才立竿见影：

| 操作 | 典型耗时 |
|---|---|
| CPU 周期 | < 1 ns |
| 机房内网络（ping） | < 1 ms |
| Redis 访问 | 1~5 ms |
| MySQL 主键索引查询 | 5~15 ms |
| 跨地域（北京-上海） | ~30 ms |
| 跨地域（北京-深圳） | ~40 ms |
| 跨国（中国-美国） | 150~200 ms |

跨地域耗时的物理下界可算：光纤折射率约 1.5，光速 v = 30/1.5 =
20 万公里/秒，北京-深圳 2000 km 单纯传播就要 10ms，叠加中继
放大、封包拆包后实际 ~40ms。**光速改不了，跨地域调用就是最贵
的操作之一。**

另一个隐藏量级：并发承受力。Redis 单机 10 万 QPS（瓶颈在带宽/
CPU），MySQL 稳定支撑 5 千并发就得读写分离 + 分库分表——
**存储选型本身就是数量级差异**。

下面按"前端接口 → 调用链路 → 存储系统"逐层削薄（三板斧合计
39 策略中的核心部分，后续 SQL/索引、异步池化等见站内关联笔记）。

## 第一板斧：接口层——别让一个接口背所有数据

**1. 核心与非核心拆分**：用户主页接口返回庞大，任一慢模块拖垮
整体、失败率上升、前端连核心数据都渲染不出。按"前端必须展示"
划线拆成多个接口——非核心接口失败可独立降级，不伤主链路。

**2. 前端并行调用**：接口设计保证可独立调用（避免"先 A 后 B"），
前端总耗时 = max(A, B) 而非 A+B。公共数据被重复查询是必要代价，
重点优化公共数据本身。

**3. 防篡改代替重复校验**：提单接口本该重新校验商品可见性/优惠
规则——用**预览 Token** 方案：预览接口校验后把结果（或其 MD5）
存缓存 15 分钟，提单时只比对一致性，不一致即伪造。校验成本从
"全链路重查"降为"一次比对"。

**4. 同步写改异步写**：耗时写接口拆两步——收请求建任务立即返回，
前端轮询结果。释放后端线程与 socket 占用，超时失败率同步下降。

**5. 页面静态化 + CDN**：商品详情页的不变部分（介绍/头图/参数）
用 Thymeleaf 渲染成 HTML，rsync 到 nginx / 注入 CDN，浏览器直接
取静态文件，详情接口的压力只剩"变化的部分"。CDN 就近分发，
顺便扛住高并发洪峰。

## 第二板斧：链路层——RPC 次数是硬通货

**6. 跨地域调用最小化**：链路图上标出每一次跨地域（RPC/DB/缓存/
MQ 都算）。上游在上海、我方双地部署、DB 主库在北京——让上游
**调用我方北京节点**（1 次跨地域），而不是上海节点反复跨地域
访问北京 DB（N 次）。

**7. 单元化架构**：多地域部署主库，用户归属最近地域、请求路由
到本地单元——像 CDN 一样"数据跟人走"，跨地域调用几乎消失，
还白赚容灾能力。需要用户路由服务 + MQ/Redis/RPC 全家桶支持
单元化。

**8. 微服务别拆过细**：一次请求穿四五个服务，每跳都是网络 I/O +
序列化 + 对方 GC 停顿——**一个大服务的性能往往优于 5 个微服务**。
经验阈值：团队人均 2 个服务以上就是过细。权衡开发效率、领域
划分与线上性能。

**9. 去中间商 / Client 化**：A→B→C→D→E 里若 B/C/D 只是转发，
让 A 直调 E；若 B 有业务逻辑，B 可发一个 Java Client jar 给 A
用（数据由 A 提供）——关注关系这类高频查询就此省掉一次 RPC。

**10. 批量化**：循环单条查询是 N 倍耗时，改批量接口；批量插库
比逐条快 3~5 倍。

**11. 并行化**：多个无依赖调用用 `CompletableFuture.allOf` 并行
编排，总耗时 = 最慢者。串行是默认习惯，并行才是主动设计。

**12. 提前过滤 + 接口拆分**：活动匹配类请求大多不满足条件——
先用人群包过滤掉大部分无效流量再走重逻辑；RPC 侧同样"核心优先、
慢数据超时即降级"。

## 第三板斧：存储层——选型即数量级

**13. MySQL → Redis**：读压力上来先做数据异构。选对结构：关注
列表用 Hash、浏览量去重用 HyperLogLog、浏览记录用 List、附近
的人用 GEOHash。选对策略：大数据量用"更新时失效 + miss 回源"，
小数据量高实时用"常驻缓存 + 定时兜底同步"。

**14. Redis → 本地缓存**：Redis 1~5ms，本地缓存近乎为零——极少
变更的热点数据（配置、开关、人群包）再往近挪一层。代价是一致性
与失效广播，参见站内缓存模式笔记。

存储之后的第四到八板斧（SQL 与索引优化、异步与池化、序列化压缩、
压测与监控等）在站内各有专门笔记，此不重复。

## 小结

- **量级感是优化第一课**：跨地域 30ms vs CPU 周期 1ns，差六个
  数量级；找到链路上最贵的一段再动手。
- 接口层：核心/非核心隔离 + 异步化 + 静态化，让慢的失败不传染；
- 链路层：RPC 次数是硬通货——并行、批量、去中间商、单元化，
  每省一跳都是白赚的毫秒；
- 存储层：选型即数量级（DB → Redis → 本地缓存），热点数据
  越近越快。
