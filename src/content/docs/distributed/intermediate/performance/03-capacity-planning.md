## 先想清楚"能扛多少"是谁的问题

三高架构（见[三高篇](/distributed/intermediate/performance/01-triple-high/)）是手段，
**容量是标尺**：不知道系统上限，限流阈值是拍脑袋，扩容时机靠
猜，压测就是给这把标尺刻度。面试问"你们系统 QPS 多少、怎么算的"，
考的正是这套推导链路。

## 容量估算：从业务数字到目标 QPS

```
日均请求量 1 亿
→ 日均 QPS = 1亿 / 86400 ≈ 1158
→ 峰值 QPS ≈ 日均 × 峰值系数（3~10 倍，业务越集中系数越高）
→ 再留出营销/突发余量，得 目标容量
```

| 概念 | 含义 |
|---|---|
| 日均 QPS | 总量摊平，几乎没参考价值 |
| 峰值 QPS | 真实高峰（午晚高峰、大促），**容量按它规划** |
| 峰值系数 | 峰值/日均，秒杀类可达百倍 |
| 目标容量 | 峰值 × 冗余系数（见下） |

**Little's Law**（高频追问）：`并发数 = QPS × 平均 RT`。QPS 1000、
平均 RT 50ms → 稳态并发 50 个请求在途——线程池/连接池大小直接
由它推出，而不是拍一个 200。

## 水位线：峰值不能跑满机器

单机容量（压测实测出的最大吞吐）有了之后，算水位：

| 指标 | 值 | 说明 |
|---|---|---|
| 单机容量 | 1200 QPS | 压测 P99 达标时的最大值 |
| 日常峰值 | 600 QPS | 水位 50%，健康 |
| 容量目标 | 800 QPS | **水位 ≤ 60~70%**，留冗余 |

为什么不能 100% 跑满：发布滚动期少一半机器、流量天然波动、
GC 与慢查询让实际容量抖动——**满水位的系统没有生存余量**。
水位长期 > 70% 就是扩容信号。

## 压测方法：单接口 → 全链路

### 单接口基准压测

先拿到每个服务的单机容量：隔离环境 + 固定数据集 + 逐步加压，
记录吞吐与 RT 曲线，找**拐点**：

- 健康段：加压 → QPS 线性升，RT 平稳。
- 临界点：RT 开始上翘，QPS 增速放缓——**最大容量在这里**。
- 过载区：RT 陡升、QPS 反而下降（排队/上下文切换/GC 吞掉吞吐）。
  拿"过载区峰值"当容量是经典错误。

### 全链路压测

单接口都达标，串起来仍可能挂（缓存击穿、连接池争抢、MQ 积压）。
全链路压测在**生产环境**用真实链路施压，配套两件基础设施：

- **影子标记**：压测请求带特殊标记（header/trace 透传），沿途
  存储落到**影子表/影子库**——逻辑同真实链路，数据物理隔离，
  绝不污染生产数据。
- **流量录制回放**：录制线上真实请求模型（接口比例、参数分布）
  回放施压，比拍脑袋构造的数据真实得多。

### 压测纪律

- 低峰期执行，预设熔断开关（异常立即停止施压）。
- 压测前明确"观察什么"：P95/P99 RT、吞吐、错误率、缓存命中率、
  连接池/线程池水位、慢查询数。
- **数据不真实 = 白测**：缓存全命中、热点 key 分布均匀的压测
  结果一律不可信。

## 从压测结果到容量动作

压测不是终点，产出的是三份可执行清单：

1. **扩容清单**：哪些服务水位超标，扩到几台（无状态水平扩）。
2. **限流校准**：各接口阈值按实测容量更新（见
   [分布式限流](/distributed/intermediate/traffic/01-distributed-rate-limiting/)），
   阈值 × 水位目标而不是机器数 × 拍脑袋值。
3. **预案清单**：压测中暴露的短板（缓存击穿、慢 SQL、MQ 积压）
   转化为降级/优化任务，进入下一轮迭代——压测报告的终点是
   排期，不是归档。

## 小结

- 容量 = 峰值 QPS × 冗余；水位 60~70% 是扩容警戒线，满水位
  系统没有生存余量。
- 并发数用 Little's Law 算，容量用拐点找：RT 上翘、吞吐停滞
  即临界，别拿过载区的峰值当容量。
- 全链路压测的命门是数据隔离（影子表）与流量真实性（录制回放）；
  压测产出是扩容/限流/预案三份清单。
