## 先理解发布节奏的变化

Java 9（2017）起从"几年一大版"改为**半年一版**：每年 3 月 / 9 月各一版，
功能没做完就下个版本再来；只有少数版本是 **LTS**（8 / 11 / 17 / 21），
生产环境实际选型都在 LTS 之间跳。理解这个节奏，"学不学得过来"的焦虑
就化解了——非 LTS 版本只是 LTS 之间的"预装配线"。

## JPMS：平台模块化（Java 9 的头号工程）

JDK 本身被拆成一堆命名模块（`java.base`、`java.sql`…），应用也可以
声明自己的模块：

```java
// module-info.java（源码根目录）
module com.demo.app {
    requires java.sql;              // 依赖哪个平台模块
    exports com.demo.api;           // 对外暴露哪些包
    opens   com.demo.entity;        // 允许深度反射（如 ORM 读字段）
}
```

三条访问规则从"全公开"变成**显式声明**：没 `exports` 的包，外部连
public 类都访问不到；没 `opens` 的包，框架深度反射读不了字段——
迁移老代码到 17+ 报 `InaccessibleObjectException`，根子就在这。

两个落地工具：

| 工具 | 干什么 |
|---|---|
| `jdeps` | 分析 jar 的模块依赖，评估能不能迁移 |
| `jlink` | 按模块裁剪出自定义精简运行时（几十 MB 的自包含 JRE） |

类加载器同步调整：Extension ClassLoader 改名 **Platform ClassLoader**，
职责边界重划 —— 详见[类加载机制与双亲委派](/java/advanced/jvm/01-class-loading/)。

> 实务视角：多数业务应用至今没写 `module-info.java`，靠 classpath
> （未命名模块）跑。但**必须懂它**——升级 JDK 后的反射报错、jlink
> 裁剪镜像、`--add-opens` 参数都源于此。

## var：局部变量类型推断（Java 10）

```java
// 右边一眼可见类型，左边省写
var list = new ArrayList<HashMap<String, User>>();
var stream = list.stream();
```

只能用于**有初始化器的局部变量**；不能用于字段、方法参数、返回值、
`var x = null`。本质是**编译期语法糖**（字节码里仍是确切类型），
不是动态类型。适用判断：**右侧类型已显而易见**才用，否则可读性倒扣。

## 常用新 API 速查（9~11）

```java
// 集合工厂方法：不可变小集合一行建（9）
List.of("a", "b");
Map.of("k1", 1, "k2", 2);
// 注意：不可变（add 抛 UnsupportedOperationException）、不允许 null

// String 补齐（11）
"  hi ".strip();        // 比 trim 强：支持 Unicode 空白
"ab".repeat(3);
"a\nb".lines().count();
"".isBlank();

// 标准化 HttpClient（11），替代老 HttpURLConnection
HttpClient client = HttpClient.newBuilder().build();
HttpRequest req = HttpRequest.newBuilder(URI.create("https://a.com")).build();
CompletableFuture<HttpResponse<String>> resp =
        client.sendAsync(req, HttpResponse.BodyHandlers.ofString());

// Files 直读直写（11）
String content = Files.readString(Path.of("a.txt"));
Files.writeString(Path.of("b.txt"), content);

// 接口私有方法（9）：default 方法之间可复用私有实现
// 单文件直接跑（11）：java Hello.java 免 javac
```

## GC 与 JVM 层面的变化

| 版本 | 变化 | 影响 |
|---|---|---|
| 9 | **G1 转正为默认收集器**，CMS 标记废弃 | Parallel 时代落幕 |
| 9 | 统一 JVM 日志框架 `-Xlog:gc*` | 老的 `-XX:+PrintGCDetails` 退役 |
| 10 | G1 Full GC 并行化 | Stop-the-world 全量回收不再单线程 |
| 10 | 容器感知（识别 cgroup 内存/CPU 限额） | 容器里 JVM 不再"看错"机器配置 |
| 11 | **ZGC 实验性引入**（红帽 Shenandoah 同期） | 低延迟收集器路线开启 |
| 11 | Epsilon GC（不回收，只分配） | 基准测试 / 短命任务专用 |

参数与选型的展开见[JVM 参数与调优](/java/advanced/jvm/07-tuning/)。

## 8 → 11 升级的主要阻力

- **内部 API 封装**：`sun.misc.*` 逐步不可见，反射 JDK 自身模块要加
  `--add-opens`（到 16/17 变成默认强封装，见下一篇）。
- **Java EE 模块移除**（11）：`javax.annotation`、`javax.xml` 等从 JDK
  剥离，老项目要自己补依赖（如 `javax.xml.bind`）。
- **字节码增强类库**：老版本 cglib/ASM 不认识新字节码版本，需升级。

## 小结

- 9 起半年一版，LTS（8/11/17/21）才是选型锚点。
- JPMS 把"全公开"改成显式 `exports/opens`；jlink 裁剪运行时；升级
  报错的两大源头是强封装与 Java EE 模块移除。
- 语法甜点：`var`（编译期推断）、集合工厂方法（不可变）、String/Files
  新方法、标准化 HttpClient。
- JVM 线：G1 接班默认、`-Xlog` 统一日志、容器感知、ZGC 试验田开张。
