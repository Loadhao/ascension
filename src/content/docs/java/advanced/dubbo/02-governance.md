## 集群容错：失败后怎么办

Consumer 面对多个 Provider，一次调用失败后按配置的容错策略收场：

| 策略          | 行为                     | 适用                          |
| ----------- | ------------------------ | --------------------------- |
| Failover    | 换一台重试，默认 retries=2      | **读接口**；写接口慎用（重复写） |
| Failfast    | 失败立即抛，只发起一次              | 写接口、新增记录                    |
| Failsafe    | 失败忽略，记日志                 | 可有可无的旁路调用（打点、通知）           |
| Failback    | 失败先返回，定时重发               | 消息通知类，最终一致                  |
| Forking     | 并行调多台，取最快成功              | 实时性要求高、资源成本敏感度低             |

**重试与幂等必须联动**：Failover 自动重试意味着同一笔请求可能到达
多次，写接口要么改 Failfast，要么把接口做成幂等——超时重试引发
的重复扣款是这一课的经典事故（幂等与状态机见
[支付系统场景](/distributed/intermediate/case-studies/17-payment/)）。

## 超时：一切治理的锚点

- 默认 1 秒偏激进，按接口 P99 实测设定；客户端超时应**略大于**
  服务端，否则服务端还在跑、客户端已放弃，线程与连接被白白占用
- 超时 × 重试次数要纳入容量预算：失败放大系数 = retries + 1，
  下游抖动时流量被放大数倍，可能压垮本想保护的系统
- 层级超时（provider 端、method 级）可覆盖全局默认，逐层收窄

## 负载均衡与降级

- 内置策略：随机（默认，权重加权）、轮询、最少活跃调用（慢节点
  自然少接活）、一致性哈希（同一参数落到同台机器，缓存友好）
- **mock 降级**：`mock=fail:return null` 或强制 `force:return`，
  依赖挂了不拖垮主流程——登录后拉「用户偏好」这类旁路依赖的标准
  姿势；服务级熔断的完整理论见 [Sentinel](/java/advanced/springcloud/05-sentinel/)
- 直连提供者（url 直连）用于联调绕过注册中心；export 与版本号
  （version/group）支撑灰度与多实现路由

## Dubbo3 的治理变化

- **应用级服务发现**：注册数据从「接口级」收敛为「应用级 + 方法
  元数据」，注册中心压力降一个数量级——从接口级迁移是 Dubbo3
  最大的运维变化
- **Triple 协议**：兼容 gRPC 的 HTTP/2 流式协议，跨语言与网关
  穿透能力补齐
- 迁移期双注册双订阅过渡，老的接口级消费方不受影响

## 要点备忘

- 容错策略按「失败的业务代价」选：读 Failover、写 Failfast、
  旁路 Failsafe
- 重试是流量放大器：超时与重试次数必须按下游容量一起算
- mock 降级保护主流程，前提是旁路依赖的返回缺失真的无害
- Dubbo3 应用级发现是为了注册中心可扩展性，迁移靠双注册平滑过渡
