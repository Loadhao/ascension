LLM 从没见过"字"，它只见 **token**——文本先被分词器切成词表里的
最小单元再进模型。"strawberry 有几个 r 数不对"、"中文比英文贵"、
"上下文窗口按 token 计"——这些现象的根全部在 tokenizer。理解它，
token 成本篇与推理参数篇的很多"为什么"就通了。

## BPE：高频子词合并

主流分词器（BPE 及其变体）的训练逻辑：从字符开始，**反复把最高频的
相邻对合并**成新词元，直到词表达到目标大小——

- 高频英文单词整词进词表（"the"），低频词被切成子词（"unbelievable"
  → "un" + "believ" + "able"）；
- 中文常见字基本一字一 token，生僻字可能被拆成字节；
- **后果一**：同一个词的 token 数不固定——token 与字符不是 1:N 的
  固定映射。

## 三个著名"翻车"的根源

| 现象 | 根源 |
| --- | --- |
| "strawberry 有几个 r"答错 | 模型看到的是 token（如 "str"+"aw"+"berry"），**没有字符级视图**，数字母是弱项 |
| 算术容易错 | 数字被切成不按位对齐的 token（"1234" 可能是一个 token），位运算直觉失效 |
| 中文/小语种成本高 | 词表中中文/小语种子词少 → 同样内容切出更多 token |

**应用层教训**：依赖"字符级精确"的任务（数字母、逐字反转、算术）
要意识到这是 tokenizer 的结构性短板——提示里把文本用空格/分隔符
拆开（"s t r a w b e r r y"）是常用的补偿技巧。

## 词表大小的权衡

- **词表大**（如 15 万）：常见词整词进表 → 序列短、成本低；但
  embedding 表大（词表 × 维度），稀有词浪费；
- **词表小**：embedding 表小，但同文本切出更多 token → 序列长、
  计算与成本高；
- **领域扩充**：医疗/法律领域可扩充领域词进词表并微调 embedding
  ——领域文本 token 数下降，成本与长度双优（但要重训分词器，
  门槛高）。

## 应用影响：一切都按 token 计

- **成本**：中文约 1 字 ≈ 1 token，英文约 4 字符 ≈ 1 token——
  Token 成本篇的估算基础；
- **窗口**：上下文窗口按 token 计（不是字符数）；
- **输出限制**：max_tokens 限的是输出 token 数——被截断的中文回答
  换算成字数比想象的少。

## 高频追问速答

- **为什么不同模型同一句话 token 数不同？** 词表与合并策略是各家
  训练出来的（BPE 变体），同一文本切分结果不同——跨模型对比成本
  要用各自的 tokenizer 实测。
- **能自定义词表吗？** 可以（领域词扩充 + 调整 embedding），但需要
  重训 embedding 与部分模型——收益是领域文本 token 下降，属于
  重度自部署才值得的优化。
- **怎么数一次请求的 token？** 用模型方提供的 tokenizer（tiktoken
  /各模型 tokenizers）实测——拍脑袋估算在预算场景会翻车（Token
  成本篇）。

## 小结

- LLM 眼里只有 token：BPE 高频合并产生词表，"字"只是 token 的
  拼装结果——字符级精确任务是结构性弱项。
- 词表大小是"序列短"与"embedding 表大"的权衡；中文/小语种
  token 密度低是成本差异的根源。
- 应用影响三处：成本估算、上下文窗口、输出截断——全按 token 计，
  实测为准。
