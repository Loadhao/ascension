Agent 的能力上限由**工具集质量**决定：模型选工具靠的是工具名与描述——
**描述就是写给模型的 API 文档**，文档写得差，再强的模型也会选错工具、
传错参数。本篇讲工具集设计的四条原则——Agent 工程里回报率最高的投入。

## 原则一：粒度——一个工具一件事

- ❌ 反例："manage_file(action, path, content)"——一个万能文件工具，
  参数组合爆炸，模型容易传错；
- ✅ 正例："read_file(path)"、"write_file(path, content)"、
  "list_dir(path)"——**小而正交的工具，模型组合使用**；
- 判断标准：一个工具的描述能不能**一句话说清**？说不清就是拆分信号；
- 对照 Unix 哲学（文本管道篇）：do one thing well，组合出能力。

## 原则二：描述——写给模型的新人文档

工具描述的质量直接决定选择准确率（可量化：评测集测工具选择正确率）：

| 要素 | 好的写法 | 差的写法 |
| --- | --- | --- |
| 用途 | "搜索代码中的符号定义（函数/类）" | "search" |
| 何时用/不用 | "已知符号名时用；要按内容全文搜用 grep" | 无 |
| 参数 | "query：完整符号名，支持部分匹配" | "query：查询串" |
| 示例 | 给 1~2 个调用示例 | 无 |

- **"何时不用"比"何时用"更防错**——明确边界让模型少走弯路；
- 参数设计**扁平优于深嵌套**：嵌套对象的参数模型传错率高；
- 描述变更要回归评测（工具描述改一个词可能改变选择行为——像改提示词
  一样有纪律）。

## 原则三：错误返回——可行动的信息

工具执行失败时，**错误信息是给模型的提示词**：

- ❌ "Error: invalid input"——模型只能瞎猜重试；
- ✅ "文件不存在：/app/config.yaml。目录下有：config.yaml、
  config.dev.yaml——是否要找的是这些？"——**告诉模型现状与可能
  的下一步**；
- 错误分类设计：参数错误（可修正重试）/ 权限错误（别重试）/ 资源
  暂不可用（稍后重试）——**不同类型触发不同行为**（错误恢复篇）。

## 原则四：数量——多则分组按需加载

- 工具超过 ~20 个，选择准确率显著下降（模型要在过多选项里挑）；
- 解法：**按任务域分组 + 按需加载**（技能加载篇的按需思想）——
  把不相关域的工具从当前上下文移除，而不是全量常驻；
- 工具的**返回值也要控制大小**：大结果截断 + 提供"获取更多"的分页
  工具——返回值也是要占上下文的（上下文工程篇）。

## 高频追问速答

- **工具选择准确率怎么测？** 评测集里给"任务 + 应选工具"标注，测
  模型选择与标注的一致率——改描述前后跑对比（应用评估篇）。
- **工具要幂等吗？** 读类天然幂等；写类工具设计成幂等（同参数重复
  执行结果不变）——重试机制的前提（幂等篇）。
- **MCP 生态的工具质量参差怎么办？** 接入前审描述与错误行为，差的
  包装一层再暴露给模型——网关思想（LLM 网关篇）在工具层的复用。

## 小结

- 四原则：粒度（一个工具一件事）、描述（新人文档+何时不用）、错误
  （可行动信息）、数量（<20 + 按需加载）。
- 工具描述 = 给模型的 API 文档——**文档质量决定选择准确率，可量化
  可迭代**。
- 错误信息是提示词：不同错误类型触发不同的模型行为设计。
